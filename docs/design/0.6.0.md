# research-agent 0.6.0: design

- Status: draft for the owner's review, 2026-10-09
- Base: `main` at `1c396d6` (plugin 0.5.0, tag `v0.5.0`)
- Input: `docs/design/respec-input-2026-10-09.md` (draft PR #6), referred to below as "the input". Where this design departs from it, section 16 gives the reason.
- Evidence read: the whole plugin at `1c396d6` and its history; `equity_research` main at `2712374`; `equity_analyst_v2` main at `03f40a6` (`scripts/research_drift.py`, `docs/agents/research.md`, `docs/research-lock.md`).

## Summary

0.6.0 turns research-agent from a plugin that one project configured by hand into a tool that any agentic system can adopt from one prompt and keep pinned to a release. It changes six things:

1. **One config file.** A project describes itself in `research-agent.toml` at its repository root. The file holds only what differs between projects: where the research lives, who decides, which consumer it serves, which environment variables its sources need, and which plugin versions it accepts. Everything else (file names, queue columns, statuses, headings, formats) is fixed in the contract. `CLAUDE.md` only points to the file. For 0.6.x the plugin still reads the old `CLAUDE.md` prose, so equity_research keeps working before it adopts.
2. **A setup skill that can adopt and check.** `/new-research-project` gains two modes beyond a fresh project: adopt an existing project (which also upgrades one), or install the consumer kit in a system that builds on research held elsewhere. It is safe to re-run, routes its interview through a host agent, and ends with a **doctor**, a script that checks the config against the files and stops on any mismatch.
3. **A consumer kit.** The plugin ships the integration prompt (about twenty lines) and the drift tool. The drift tool generalises the 155-line script equity_analyst_v2 wrote by hand, and it also pins the domain rules a consumer's code implements. The app replaces its three hand-written files with the kit.
4. **A fixed hand-back.** Every run ends with the same block: status, answer, proposed decisions, open items, flagged content, lesson candidates, spend, paths, and the plugin version.
5. **Releases and sprints.** Versions change only at release, with a CHANGELOG, an immutable git tag, and consumers pinning a tag. Tool lessons go to a GitHub issue inbox and are sorted into the next release. Field lessons go to the project's domain rules.
6. **Domain neutrality and rule IDs.** Finance examples leave every file a run reads. Each domain rule gets a stable ID and fields, prompts cite IDs instead of retyping rules, and the log records which rules each question group passed.

The research protocol itself does not change. It keeps the same intake, evidence standards by claim type, verification in code, independent review and decision session. fetch_raw keeps all of its fidelity behaviour. Accuracy stays the first test for every choice below. Where convenience and the fidelity of facts or numbers pulled in different directions, fidelity won. Examples are the doctor stopping rather than guessing, the identity map staying out of reach of a pull request, and the drift tool keeping its hash function byte for byte.

## Terms

- **Host:** the agentic system that adopts the plugin. A host can be a **research project** (a repository that runs research, such as equity_research), a **consumer** (a system that builds on another repository's accepted decisions, such as equity_analyst_v2), or both at once. A **generalist host** is a single agent that codes, designs and runs its own subagents, and keeps its research in its own repository.
- **Contract:** what a host may depend on, listed in `CONTRACT.md`. It covers names, paths, formats and behaviours.
- **Doctor:** the check script that compares the config with the files on disk.
- **Pin:** a row in the consumer's lock file. It records a decision or rule, the research commit it was read at, and a hash of its text.
- **Drift:** a pinned item that changed, was superseded or disappeared on the research repository's main branch after it was pinned.
- **Hand-back:** the fixed block a run returns to its host.

## 1. Architecture: core, setup and consumer kit

The plugin has three parts. Each part has one job and one kind of user.

| Part | Contents | Who uses it | Changes in 0.6.0 |
|---|---|---|---|
| **Core** | `research-protocol`, `research-writing` and `run-next-task` skills; `researcher` and `reviewer` agents; the `fetch_raw` MCP server | Every research run | Reads the config; runs the doctor at the start; writes the hand-back and the applied-rules table; scopes lessons; neutral examples |
| **Setup** | `new-research-project` skill, its templates, `tools/doctor.py` | A host, once per adoption or upgrade, and the doctor at every run | Modes new, adopt (which also upgrades) and consumer; host-routed interview; doctor |
| **Consumer kit** | `kit/INTEGRATION.md` (the integration prompt), `kit/research_drift.py` | Any host; copied into it by setup | New |

The core never writes outside the project it serves. Setup writes only files the project does not have yet, plus the changes it lists and the host confirms. The kit runs inside the host and reads the research repository only through git.

The parts meet through the contract. The core reads `research-agent.toml` and the fixed layout. Setup writes them. The kit reads the research repository's config and decision headers at a git ref. Nothing else crosses between them.

The kit is **copied** into the host (`.research-agent/`), not run from the plugin's install directory. There are three reasons. A consumer that never runs research, such as the app in CI or a cloud session, may not have the plugin installed. The plugin's install path is not visible outside Claude Code: `${CLAUDE_PLUGIN_ROOT}` is substituted in skill text, not set in the shell. And a copy is reviewed in the host's own pull request, which matches the owner's rule that third-party code is inspected before it runs. Each copied file carries a stamp line with the plugin version and the sha256 of the rest of the file, so the doctor can detect both a version outside `requires` and a local edit. Section 18, question 1 gives the alternative.

## 2. The config file holds only what varies

### Schema

`research-agent.toml` sits at the repository root, a fixed path, so every tool finds it without reading prose. TOML (a strict config format) replaces the YAML of the input's sketch. Section 16 gives the reason.

```toml
# research-agent.toml: equity_research after adoption (values are REAL)
requires = ">=0.6.0, <0.7.0"          # plugin versions this repository works with

[project]                              # present when research runs in this repository
root = "docs/research"
brief = "strategy-research-brief.md"   # optional; default "research-brief.md"
decider = "requester"                  # who accepts, rejects or defers decisions
env = ["EDGAR_IDENTITY", "FRED_API_KEY"]   # variable names only, never values

[project.consumer]                     # optional: the system this research serves
name = "equity_analyst_v2"
context = "app-context.md"             # under root

[project.fetch_identity]               # optional: declares the identity map; the operator sets
"sec.gov" = "EDGAR_IDENTITY"           # FETCH_RAW_IDENTITY_HOSTS to match, and the doctor compares

[project.run_defaults]                 # optional; else references/effort-and-cost.md
effort = "xhigh"
```

```toml
# research-agent.toml: equity_analyst_v2 after adoption
requires = ">=0.6.0, <0.7.0"

[consumes]                             # present when this repository builds on decisions
research = "dadahabib1/equity_research"   # owner/repo, or "self" for research in this repository
clone = "../equity_research"           # optional; default ../<repo name>
```

A generalist host that runs research and builds on it in the same repository has both tables, with `research = "self"`.

### Why each field varies

| Field | Why it differs between projects | Evidence |
|---|---|---|
| `requires` | Each host upgrades on its own schedule; audit item 13 asks the consumer to declare a range | Structural problem 2 in the input: sessions ran different builds |
| `project.root` | A generalist host may keep research outside `docs/research` | Undefined path roots (input §4, problem 5) |
| `project.brief` | equity's brief is `strategy-research-brief.md`; the new neutral default is `research-brief.md` | 13 equity prompts name the old file |
| `project.decider` | The owner decides for equity; a team or a host's user decides elsewhere | Audit item 3 |
| `project.consumer` | Some research serves an app; some serves only its requester | equity's `app-context.md` |
| `project.env`, `project.fetch_identity` | They depend on the field's sources: SEC requires an identity, most sources need none | equity domain rules heading 6; fetch_raw's `FETCH_RAW_IDENTITY_HOSTS` |
| `project.run_defaults` | Budget differs | equity's $30-a-month budget |
| `consumes.research`, `consumes.clone` | Which repository holds the research, and where it is cloned on this machine | The app's `--research` default |

Unknown keys are a doctor failure, so a misspelt key cannot be silently ignored.

### What the contract fixes instead

- **Layout under `root`:** `domain-rules.md`, `research-queue.md`, `prompts/`, `logs/`, `decisions/` with `decisions/INDEX.md`, and an optional `templates/` whose files override the plugin's templates of the same name. equity already uses this layout, so adopting it moves no files.
- **`<topic>`:** the deliverable's file stem, taken from the queue row's Deliverable column (`system-review-v1.md` gives `system-review-v1`). The deliverable is `<root>/<topic>.md`, the log is `<root>/logs/<topic>-log.md`, and the branch is `research/<topic>`. Before 0.6.0 `<topic>` was undefined (input §4, problem 5).
- **The queue:** the required columns Task, Prompt, Deliverable, Prerequisites and Status; the six statuses; and the selection rule. Extra columns are allowed. equity has Requested by and Blocks.
- **The brief's nine headings, the domain rules' eight headings and their rule format (section 6), the log's sections, the decision header block (section 5) and the hand-back (section 4).**
- **The hand-over:** a branch `research/<topic>` and a pull request against the remote's default branch. With no remote or no `gh`, the run commits on the branch and the hand-back says "pull request: none". This fallback depends on the environment, so it needs no setting.
- **Lessons:** tool lessons go to the plugin's own repository, named by `repository` in its `plugin.json`. Field lessons go to the domain rules (section 6).
- **Consumer files:** the lock at `docs/research-lock.md` and the kit in `.research-agent/`.

### One-version fallback to the old prose config

When `research-agent.toml` is missing and `CLAUDE.md` has a "Research" section, 0.6.x reads the paths from that prose as 0.5.0 did. The log header then records `config: legacy CLAUDE.md prose (deprecated; removed in 0.7.0)`, and the doctor reports DEPRECATED, not FAIL (the per-check table in section 3). 0.7.0 removes the fallback. equity_research therefore keeps running on 0.6.0 before it adopts, and adoption is a pull request it can schedule.

## 3. Setup and doctor

### `/new-research-project` detects its mode and is safe to re-run

The skill looks at the repository and states the mode it will use before writing anything. The host or user confirms.

| Mode | Detected when | What it writes |
|---|---|---|
| **new** | No config and no research files | Config; brief, domain rules and queue from templates; `templates/prompt.md` copied into the project, so a host can fill a prompt from a file on disk; `prompts/`, `logs/`, `decisions/INDEX.md`; consumer context file if a consumer is named; PR template; `CLAUDE.md` pointer; `.gitignore` lines; pinned plugin enablement |
| **adopt** | Research files exist, with no config or with a config whose `requires` excludes the installed version | Without a config: a config that matches the existing files, read from the `CLAUDE.md` prose and the files themselves, and the `CLAUDE.md` pointer replacing the prose paths. With one: the new `requires` and the mechanical steps in `UPGRADING.md`. In both cases: any file new mode writes that is missing, such as `templates/prompt.md`; and a list of the content changes the contract asks for (such as rule IDs) and of the steps a person must take, as proposals |
| **consumer** | The host builds on research held elsewhere (it asks) | A `[consumes]` table; `.research-agent/INTEGRATION.md` and `.research-agent/research_drift.py`; `docs/research-lock.md` if missing; `CLAUDE.md` pointer |

Upgrading is adopt on a project that already has a config. Both read what exists, bring it to the installed contract and list what needs a person, so one mode does both with one detection branch fewer.

Every write is "create if missing; otherwise compare and report". The skill never overwrites project content, never deletes a file, and never edits an accepted decision record. A second run on a project that passed the doctor changes nothing, which is trial check 2 in section 14. Setup leaves its changes in the working tree, and the host commits them its usual way.

The skill writes these from templates, where the files are missing:

- the decision-record template with the header block;
- `decisions/INDEX.md`;
- the consumer context file;
- `.github/pull_request_template.md` for task and decision-session pull requests, skipped if the host already has one;
- `.gitignore` lines for `__pycache__/` and `*.pyc`. equity_research has no `.gitignore`, and committed `.pyc` files blocked its PR #4.

"Pinned enablement" is a `.claude/settings.json` marketplace entry carrying `"ref": "vX.Y.Z"` (section 9).

### The interview goes through the host

The interview is the one that fills the brief and the domain rules (today's step 3). When a host agent runs the skill, the host answers each question from what its own system records. Each such answer is labelled `[PROVIDED: project]` with its source and date. The host passes to its user only what it cannot answer: decisions, and facts about the requester. The skill records every answer's source (requester, `[PROVIDED: project]`, looked up, or assumption), as `intake.md` already does for runs. The interview asks each question once. It does not ask the host and then the user.

### The doctor stops on any mismatch

`tools/doctor.py` is a script with PEP 723 inline metadata, run as `uv run --script ${CLAUDE_PLUGIN_ROOT}/tools/doctor.py`. Claude Code substitutes the path in skill text. The script depends on PyYAML, pinned and locked like fetch_raw, to parse decision headers. Setup runs it last. `/run-next-task` runs it as its step 0. A host may run it at any time. Both skills declare `allowed-tools: Bash(uv run --script ${CLAUDE_PLUGIN_ROOT}/tools/doctor.py *)` in their frontmatter, so unattended runs are not stopped by a permission prompt.

The doctor reports each item as FAIL (exit 1: the run or setup stops), WARN (exit 0, listed in the log header) or DEPRECATED (exit 0: it works now and fails in 0.7.0). Exit 2 means the doctor could not run, for example because uv or git is missing. It prints variable names only, never values. A project without a config runs on the legacy fallback (section 2), and some checks are softer there, so that equity_research passes before and during adoption:

| # | Check | 0.6.x with config | 0.6.x legacy prose | 0.7.0 |
|---|---|---|---|---|
| 1 | Config parses, has no unknown key, and `requires` includes the installed version | FAIL | DEPRECATED (no config; range not checked) | FAIL |
| 2 | Every fixed path and configured file exists: root, brief, domain rules, queue, `prompts/`, `logs/`, `decisions/INDEX.md`, consumer context file | FAIL | FAIL, on the prose paths | FAIL |

| 6 | Each decision header parses, has the core keys, and matches its `INDEX.md` row on name and status | FAIL | FAIL | FAIL |
| 7 | `CLAUDE.md` points to `research-agent.toml` | FAIL | DEPRECATED | FAIL |

## 4. The hand-back is one fixed block

Every run ends with this block, both as the final section of the pull request body and as the session's last message. It replaces today's "five-line summary". A host can find it by its heading and read it by its labels.

```markdown
## Hand-back

- Status: in review | waiting on requester | stopped: <reason>
- Answer: <two to five sentences: what the research found>
- Proposed decisions:
  - `<decision-name>`: <one-sentence decision>. Parameters: `<name>` = <value> <unit> per <denominator>; … Evidence: §<n>, <claim type>, <grade or "measured" or "documented">. Touches: <accepted decision names, or "none">.
- Open items:
  - <item, with the evidence that would resolve it; for "waiting on requester", the questions>
- Flagged content:
  - <URL>: <what the text tried to do> | none
- Lesson candidates:
  - [tool] <rule>. Incident: <what happened in this run>. Check: <how a reviewer verifies it>.
  - [field] <rule ID, or "new">: <proposed rule>. Incident: <…>. Check: <…>.
- Spend: <tokens or cost>; model <model>; effort <level>
- Paths: deliverable `<path>`; log `<path>`; notes `<paths>`; scripts `<paths>`; branch `research/<topic>`; pull request <URL | none>
- Plugin: research-agent <version>; config <research-agent.toml | legacy prose>
```

One field goes beyond the input's list (section 16, revision 8). **Status** lets a host tell a finished run from one waiting on a question without reading the queue. The version label is enough to identify the code that ran: an install pinned to a tag is a frozen copy of that release, and versions change only at release (section 9).

Proposed decisions are proposals. Only the decider makes decisions, in a decision session.

## 5. The drift tool generalises the app's script

### Interface

```
python .research-agent/research_drift.py [--research PATH] [--ref REF] [--no-fetch]
python .research-agent/research_drift.py --hash decision <record path> <decision-name>
python .research-agent/research_drift.py --hash rule <rule-id>
python .research-agent/research_drift.py --help      # also explains every report and its action
```

The script uses only the standard library and needs Python 3.11 or later for `tomllib`. It finds the host's `research-agent.toml` by walking up from the working directory. It reads `[consumes]` and fetches the research clone, unless `--no-fetch` is given. It then reads the research repository's own `research-agent.toml` at `REF` (default `origin/main`) to find `root`, the decisions folder, the domain rules file and the consumer name. If that file is absent, it falls back to `docs/research` and prints DEPRECATED. Exit codes stay as they are: 0 means no drift, 1 means drift or pending rows, 2 means a setup error.

### Pin file format

The lock stays at `docs/research-lock.md`, a Markdown table that people review in spec pull requests. The decisions table keeps the app's columns exactly, so its 12 existing rows carry over unchanged. A second table holds the rules.

```markdown
## Locked decisions

| Decision | Record | Research commit | Content hash | Used by | Read |
|---|---|---|---|---|---|

## Pinned rules

| Rule | Research commit | Content hash | Implemented in | Read |
|---|---|---|---|---|
```

A "Research commit" of `pending <PR URL>` marks a row that waits for a research merge, as today.

### Decision header block

Each decision subsection in a record opens with a fenced `yaml` block. The core keys are below. The drift tool reads only `name`, `status` and `supersedes`. The doctor checks them all.

```yaml
name: <decision-name>            # stable kebab-case; equals the subsection heading's name
status: accepted                 # accepted | rejected | deferred | superseded | withdrawn
decided: YYYY-MM-DD
decided_by: <the config's decider>
depends_on: [<decision-name>]    # [] when none
supersedes: [<decision-name>]    # or a quoted string naming a document and section
parameters:                      # [] when none
  - {name: <name>, value: <value>, unit: <unit, per denominator>, source: "<deliverable> §<n>"}
```

A project may add keys. equity keeps `moves_valuation` and `app`. This header is equity's block minus those two keys, so every existing equity record already conforms and none needs editing.

### Reports

| Report | Meaning |
|---|---|
| `PENDING` | The row waits for a research pull request to merge |
| `CHANGED` | The pinned decision's or rule's text hashes differently on `REF` |
| `SUPERSEDED` | An accepted decision on `REF` supersedes a pinned one |
| `STATUS` | A pinned decision is no longer `accepted` |
| `MISSING` | The record, decision or rule is gone from `REF` |
| `NEW` | An accepted decision, or a rule whose `Host:` names this consumer, that the lock does not hold |

Retiring a pinned rule adds a `Retired:` line, which changes its hash, so `CHANGED` reports it with no separate code.

Rule reports name the rule, for example `CHANGED  rule known-at-filing-date`. `--help` prints this table with the action for each report. That table is the part of the app's `docs/agents/research.md` that every consumer needs. The help text, not a separate document, becomes its single source.

### What is kept from the app's script, and what is added

- **Kept byte for byte:** the section extraction (from a `### <name>:` heading to the next `###` or `##` heading) the hash (lines right-stripped, joined with `\n`, sha256, first 12 hex characters), and the lock parsing, which strips backticks from each cell. The app's 12 existing hashes therefore stay valid, and section 13 tests this.
- **Generalised:** the research repository, clone path, decisions folder and ref now come from the two config files instead of constants. `research = "self"` covers a generalist host. Each report gets its action in `--help`.
- **Added:** rule pins, using the same extraction and hash on the domain rules file; the stamp line with its content hash; the legacy fallback.

## 6. Domain-rules lifecycle

### Rule format and IDs

Each rule becomes a `###` subsection under its numbered heading. The doctor and the drift tool can then find it the same way they find a decision.

```markdown
## 1. When information counts as known

### known-at-filing-date: Filing-based figures count as known at their filing date, not at their period end.
- Check: every filing-based input in the log names its filing date.
- Scope: decision-critical
- Source: requester, 2026-10-07 (from the plugin's former finance.md at c8310e9)
- Added: 2026-10-07
- Host: equity_analyst_v2
```

- **ID:** kebab-case, unique in the file, never renamed or reused. An edit keeps the ID, and the drift tool reports it as CHANGED. A rule is never deleted. It gets a `Retired: <date>; <reason>` line, so that citations in old logs still resolve.
- **Scope:** `decision-critical` or `all`, using the definition fixed in the template's preamble.
- **Source:** the owning source with a date, a decision record name, an incident (a log path), or the requester with a date.
- **Host** (optional): the configured consumer's name, set when that consumer's code implements the rule. A rule whose fact an accepted decision already states is not marked, because the consumer already pins that decision, and one fact pinned twice drifts twice. For equity, the trust-tier rule is the first candidate (§18, Q3). The example above shows the format only: its fact is the accepted decision `known-from-rule`, so it would carry no `Host:` line. The consumer pins such rules in its lock, and its drift check covers them.

The template's preamble fixes the three rules equity_research wrote in PR #5 (`bbac52c`), so every project has them:

- **precedence:** accepted decision records override the domain rules, and a decision that changes a rule changes it in the same pull request;
- **change rule:** runs propose changes and never edit the file;
- **"decision-critical":** its definition.

### Citing IDs instead of retyping rules

Prompts, researcher delegations and reviews cite rule IDs. A delegation still quotes each rule's text next to its ID, because the researcher cannot read files. That text is copied from the file, not retyped. This ends the drift that equity's prompts 07 to 13 show: each carries its own "Technical evidence" section, seven copies of one rule.

### Applied-rules record

The log template gains a section after Verification:

```markdown
## Applied rules

| Question group | Rule ID | Result (pass / fail / n/a) | Where shown |
|---|---|---|---|
```

Each question group lists every rule in scope for it. The reviewer checks three things. Every decision-critical rule in scope has a row. Every `fail` is resolved or carried as an open item. Every `n/a` gives a reason in Where shown.

### The learning route

Protocol step 10 splits lesson candidates by scope:

- **`[tool]`:** the lesson is about how research is done in any field. It goes in the hand-back, and the host files it as an issue in the plugin repository (section 9). The plugin's maintainer decides whether it enters `takeaways.md`.
- **`[field]`:** the lesson is about this project's field. It goes in the hand-back and in the deliverable's "Changes to existing decisions or methods" section, as a proposed rule with an ID (an existing one, or "new"). The decider accepts or rejects it in the decision session. An accepted rule is written into the domain rules in the same pull request as the decision record.

Audit item 6 (a separate project lessons file) stays rejected, as the session ruled. Field lessons have one home, the domain rules.

## 8. The integration prompt

The plugin ships this text as `kit/INTEGRATION.md`, versioned with the contract. A host receives it pasted, or reads its copy in `.research-agent/`. It follows the input's six points and, per input §2, says no more than a host needs.

```markdown
# Adopting research-agent (contract 0.6)

research-agent runs research projects: questions that need cited evidence and checked numbers before someone decides, answered under a fixed protocol that ends in a pull request and a decision session. Use it for those; answer quick lookups yourself.

1. **Set up.** Enable the plugin pinned to a `v0.6.x` tag and run `/new-research-project` in the repository that will hold the research, or, if your research lives in another repository, in your own to install this kit. Answer its questions from what your system already records, labelled `[PROVIDED: project]`, and ask your user the rest. Done when its doctor reports no FAIL.
2. **Add a task.** Fill a prompt from `templates/prompt.md` and add a row to `research-queue.md`, both under the `root` that `research-agent.toml` names, the way you make any other change to that repository. Your other changes there are the consumer context file; deliverables, logs and decision records change only through runs and decision sessions.
3. **Run it.** `/run-next-task`, in the foreground, a background agent or a cloud session; one task per session.
4. **Read the hand-back.** The run's pull request ends with a `## Hand-back` block: status, answer, proposed decisions, open items, flagged content, lesson candidates, spend, paths, plugin version. Proposed decisions are proposals: the decider accepts, rejects or defers them in a decision session, and you build only on decision records marked `accepted` on the research repository's main branch.
5. **Keep it current.**
   - **Pins.** When your work starts relying on an accepted decision, or on a domain rule whose `Host:` names you, add it to `docs/research-lock.md` with the hash from `.research-agent/research_drift.py --hash`. Run `.research-agent/research_drift.py` at startup and before writing a spec; `--help` gives the action for each report.
   - **Context.** Keep the consumer context file true to what your system can do today.
   - **Lessons.** File each `[tool]` lesson candidate as an issue on the plugin's repository with the label `lesson`. `[field]` candidates reach the domain rules through the decision session.
```

Choices behind the text:

- It names its leading words (research project, hand-back, decider, pin) once, and later steps reuse them.
- Each step ends on something the host can observe, such as "no FAIL" or the `## Hand-back` heading.
- The one guardrail is phrased as the positive list of what a host may change.
- What a host does with an accepted decision inside its own process, such as equity's mapping of decision fields to tickets, is left to the host.
- People appear only where they must: the decider, and merges where the host's process requires them (input §6).

## 9. Releases, sprints and the lessons inbox

- **Versions change only at release.** Pull requests add a line under `## Unreleased` in `plugins/research-agent/CHANGELOG.md` and leave the version alone. A release pull request does three things: it moves Unreleased under `## X.Y.Z (date)`, sets `version` in `plugin.json`, and updates `UPGRADING.md`. After its merge, the owner tags the merge commit `vX.Y.Z` and publishes the section as the GitHub release notes. A tag is never moved, so a fix is a new patch release. The repository's `CLAUDE.md` rule "bump after any change under `plugins/research-agent/`" is replaced by these rules.
- **The version leaves `marketplace.json`.** `plugin.json` is the single source. The Claude Code docs say the manifest's version takes precedence and that the marketplace entry's version is optional (marketplace reference, plugin entries).
- **The contract history moves into the CHANGELOG.** Each release gets a "Contract" subsection, and `CONTRACT.md` keeps only the current contract. The history then lives in one place.
- **Consumers pin a tag.** In project settings, the marketplace source carries `"ref"`:

  ```json
  "extraKnownMarketplaces": {
    "personal-agents": { "source": { "source": "github", "repo": "dadahabib1/research-agent", "ref": "v0.6.0" } }
  }
  ```

  Manually, `/plugin marketplace add dadahabib1/research-agent@v0.6.0`. The docs accept `owner/repo@ref` and `#ref`; build step 0 verifies this.
- **Cloud sessions pin `PLUGIN_REF`.** The owner's setup script installs the plugin, since repository settings do not install plugins in cloud sessions (input §8). It starts with one line, `PLUGIN_REF=v0.6.0`. The install line and the fetch_raw pre-warm URLs use that variable. Editing that line changes the script, which forces a rebuild of the cached environment.
- **The lessons inbox is GitHub issues** in `dadahabib1/research-agent` with the label `lesson`. Each issue gives the rule, the incident, the check, and the run it came from (repository and pull request). Only `[tool]` lessons go there. `[field]` lessons never do, so the inbox needs no scope label.
- **A sprint** is the stretch between releases. At a sprint review the owner sorts every open `lesson` issue three ways: into the next release's milestone, closed as already covered (naming the entry), or closed as rejected. The release adds accepted lessons to `takeaways.md` and closes their issues.
- **Packaging (audit item 12).** `plugin.json` gains `license` (`"MIT"`, matching the root `LICENSE`), `repository` and `homepage`. `LICENSE` is copied into `plugins/research-agent/`, because installs copy only the plugin directory.

## 10. Compatibility and versioning rules

- **Before 1.0:** a minor bump (0.Y.0) may change the contract. A patch (0.Y.Z) never does. This continues the rule the repository already states.
- **From 1.0:** a major bump changes or removes a contract element, a minor bump only adds to it, and a patch changes neither.
- **The contract** is everything `CONTRACT.md` lists. 0.6.0 adds the config schema, the fixed layout, the decision header core keys, the rule format, the hand-back, the lock format, the kit file paths and their command lines, and the doctor's exit codes.
- **Deprecation.** An element to be removed is marked "Deprecated in X; removed in Y" in `CONTRACT.md`. It keeps working for at least one minor release before 1.0, and one major release after. The doctor reports it as DEPRECATED, and `UPGRADING.md` gives the migration. 0.6.0 deprecates the prose config and domain rules written as bullets without IDs.
- **The consumer declares a range** in `requires`. Comparators are `>=`, `>`, `<=`, `<` and `==`, and a comma means "and".
- **The run checks it.** The doctor at `/run-next-task` step 0 fails when the installed version is outside the range, and the run stops before intake. The drift tool warns when its own stamp is outside the host's range.

## 11. fetch_raw: kept as is, with the identity map declared in the config

These facts from input §9 stay true in 0.6.0, and the contract keeps them.

- **Tool name:** `mcp__plugin_research-agent_fetch-raw__fetch_raw`, bundled through `.mcp.json` and run with uv as a PEP 723 script with a lock file.
- **Fidelity:**
  - the whole page is converted, with no readability-style extraction;
  - tables keep every cell;
  - superscripts become `^[x]` and subscripts `_[x]`;
  - PDFs come back per page, with exponents rebuilt from character size.
- **Labels:**
  - decision-critical values are raw-fetched or confirmed by a second route;
  - WebFetch is for discovery only, and its values are summary-fetched;
  - a BLOCKED result is a dead end to log, never content.
- **Firecrawl:**
  - it is a fallback transport only, through `rawBase64`, and our own converter always converts its output;
  - its markdown output is never used for values;
  - its search is acceptable as a second discovery route.
- **The evidence behind these rules:**
  - Jina's default mode silently dropped sections;
  - Firecrawl's markdown turned `0.00056^5` into `0.000565`;
  - Agent-Reach was rejected;
  - the NYSE page returned a Cloudflare block with HTTP 200 on one call in ten.

**The server code does not change.** `FETCH_RAW_IDENTITY_HOSTS` stays the server's only input. The operator sets it in the environment, and it is not deprecated. The config's `[project.fetch_identity]` declares the same map, so that the project's sources are on record, and doctor check 9 compares the two.

The server must not read the map from the repository. `net.py` (lines 70 to 83) sends the named variable's value to every host that matches the suffix. If the map came from a file in the repository, one line in any pull request, such as `"attacker.example" = "FIRECRAWL_API_KEY"`, would send a secret to an attacker's host on the next run. Kept in the environment, such a line only makes the doctor fail.

These rules also stay:

- a matching host receives the identity, re-checked after each redirect;
- the identity never goes to Firecrawl or into a file;
- a missing variable is an ERROR.

**Still open, carried forward unchanged:**

- the first cloud run: proxy path, certificates and the pre-warm lines;
- Firecrawl getting past a live Cloudflare block;
- multi-column PDFs interleaving their lines;
- content hidden by CSS being kept.

## 16. Revisions to the input

Each change below departs from the input, with its reason.

1. **TOML, not YAML, for the config.** Python reads TOML with the standard library (`tomllib`, 3.11 and later), so the drift tool copied into hosts needs no dependency, as the app's script needs none today. TOML also has no implicit type conversions. Decision headers stay YAML because existing accepted records cannot be edited.
2. **`contract: "0.6"` becomes `requires`, a version range.** Audit item 13 asks the consumer to declare a range. A single label cannot express "0.6.0 or later, before 0.7.0".
3. **`paths` shrinks to `root` plus an optional `brief`.** No project in evidence names its files differently, and every extra path is a case that the doctor, the drift tool and the contract must handle. The brief is the one exception, because equity's file name differs from the new neutral default.
4. **`handover` is dropped.** This applies audit item 10's ruling not to over-instruct. A branch and a pull request are always right. Whether a remote exists is a fact about the environment, not a preference.
5. **`lessons` is dropped.** The tool inbox is the plugin's own repository, already named in `plugin.json`. The rejection of audit item 6 fixes the field route. A setting for either could only be set wrong.
6. **`consumer` splits into `[project.consumer]` and `[consumes]`.** One schema then serves a research project, a consumer, and a generalist host that is both.
7. **The doctor's environment checks are split, pending the owner (§18, Q4).** Other `env` names only warn, because equity's SEC rule treats a missing identity as `[UNVERIFIED]` values and lets the run continue. An identity variable that is missing, or that does not match the config, is proposed to stop the run before it spends anything. The input's "stops on any mismatch" is kept for config against files.
8. **The hand-back adds `Status`.** Status separates finished runs from waiting ones.
9. **The consumer-context age warning runs on the consumer side.** The research repository cannot see a private consumer's release tags.
10. **The kit is copied into the host, not run from the plugin.** §1 gives the reasons. Section 18, question 1 asks the owner to confirm.
11. **The contract's change history moves to the CHANGELOG.** This keeps one place for history once a CHANGELOG exists.
12. **The brief's default name becomes `research-brief.md`.** "Strategy" is finance residue for other fields.
13. **The identity map does not move into the config as the server's input** (input §9: "moves into the config file's `fetch.identity`"). The config only declares it, and the server keeps reading `FETCH_RAW_IDENTITY_HOSTS` from the environment. A map read from the repository would let one line in a pull request send a secret to any host (§11).
