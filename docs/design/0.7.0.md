# research-agent 0.7.0: design

Scope, as approved at the sprint review of 2026-10-10: parallel runs (#28), the model named by reference (#42), the removals 0.6.0 deprecated, and the partial-supersession report 0.6.1 deferred. `CONTRACT.md` holds the result; this note records why it has this shape.

## 1. Parallel runs (#28)

**Problem.** `/run-next-task` took the first `todo` row on the default branch, but a finished run set `in review` only on its own branch. Until that pull request merged, a second run read `todo` and took the same task, or mistook the finished branch for a stopped run to resume. Every run also committed a one-word status change to the one queue table, so two runs' pull requests, or a run's and a decision session's, conflicted on adjacent lines.

**Decision.** Runs stop editing the queue. A run's state is derived from its branch `research/<topic>`, the latest pull request from that branch and the hand-back's Status; the queue keeps only what people write (`todo` when a task is added, the outcome in the decision session). The selection rule skips a task whose run is running, in review, waiting or done, and resumes a stopped one.

**Why a script.** The rule has seven states read in a fixed order and an atomic claim. Prose for a model to follow would be applied differently by different sessions, and could not be tested. `tools/next_task.py` applies it, and `tools/tests/test_next_task.py` runs it against real git with a local bare remote and a fake pull request list.

**The claim.** Each run pushes an empty commit, with a random token in its subject, to `research/<topic>` before it reads anything else. A push without force fails when another run moved the branch first, so of two runs that read the same state, one wins and the other takes the next row. The token matters: two runs claiming from the same default-branch commit in the same second would otherwise create the same commit, and the second push would succeed as "up to date". A resumed run claims on the branch's tip, so the same race resolves the same way. Replacing an abandoned or merged branch uses `--force-with-lease` on the tip the run read, which also fails if anyone moved it. The claim commit stays at the tip until hand-over (a run makes no other commit before step 7), which is how other runs see the run as in progress.

**Hand-over order.** A new run pushes, then opens its pull request; in between, its branch has no pull request and still reads as running. A resumed run replaces its pull request's hand-back first, then pushes; in between, the claim commit is still the tip. Either way no session sees a stale `stopped` status on a branch someone holds.

**Alternatives not taken.** One status file per task (the issue's second option) still needs a commit on the default branch to claim, which protected branches forbid. A draft pull request as the in-progress marker cannot be claimed atomically: two sessions can both mark one draft. Reading the branch alone, without pull requests, misses a merged run whose branch was deleted on merge; the log on the default branch covers that case, so the no-`gh` mode uses it.

### Risks from the sprint review

1. **No remote or no `gh`.** Three modes. With `gh` able to read the remote's pull requests: as above. With a remote but no such `gh`: states come from the remote's branches, with the hand-back at the end of each branch's log standing in for the pull request's, and claims are pushed the same way; for this the hand-back now also ends the log. With no remote: local branches, one run at a time per clone, no claim commit.
2. **Two runs seconds apart.** The pushed claim commit above.
3. **Abandoned pull requests.** A closed, unmerged pull request whose branch remains reads as abandoned and is taken like a free task; its branch is replaced under a lease. One whose branch was deleted reads as free.
4. **The queue no longer shows `in review`.** Stated in the queue template, `INTEGRATION.md`, the README and `UPGRADING.md`, each with where to look: the pull request's hand-back, or `next_task.py --list`. The decision session's checklist now sets the row, so the queue still records outcomes.
5. **`requires = ">=0.6.0, <0.7.0"`.** Fails check 1 on 0.7.0 by design (a minor release changes the contract). `UPGRADING.md` gives the exact edit to `>=0.7.0, <0.8.0`.

## 2. The model by reference (#42)

The contract asked for the model in the deliverable's heading, the log header and the hand-back, while a host's instructions forbade model identifiers in repository files. Where that holds, those places write `by reference` and the session's closing message names the model. The pull request body's hand-back follows the files, since a host that forbids identifiers in the repository is unlikely to want them in its pull requests. No config key: the run reads the host's instructions.

## 3. Removals and the partial-supersession report

- **Legacy prose config.** The doctor no longer reads paths from the `CLAUDE.md` "Research" section. With no config, check 1 FAILs and names the setup mode (adopt when that section exists, else new), so `/new-research-project` still detects adopt mode. The drift tool exits 2 on a research repository without a config instead of reading `docs/research`.
- **Bullet rules.** Check 4b FAILs. The one research project we know of already passes the 0.6.2 doctor with no DEPRECATED item, so no known project breaks.
- **`PARTIAL`.** 0.6.1 stopped reporting a quoted part of a decision (`"<decision> rule 2, detection only"`) as SUPERSEDED, and left the partial case to the NEW report. `PARTIAL` names the pinned decision, the quoted part and the new decision. It is reported only while the new decision is outside the lock, so pinning it, which the action asks for, ends the report; the old row stays, because the rest of the old decision holds.
